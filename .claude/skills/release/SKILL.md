# release — إصدار «حاضر»

**القاعدة (المالك): لا يُسلَّم zip إلا بعد نجاح كل الاختبارات، ومعه سطر خلاصة واحد.** لا تُرسل للمالك نسخًا بناها بنفسه، ولا تغيّر `min_ext_version` إلا إن طلب.

1. **حدّد مستوى الاختبار من نوع التعديل** (`git diff main --stat -- extension/`):
   - منطق التعبئة، التواريخ، مطابقة الدروس، الحفظ (`semester.js` منطقيًا، `engine.js`، `match.js`، `packages.js`، `dates.js`، `remote.js`) ← `full`.
   - نصوص أو شاشات أو مسار المعالج فقط ← `short`.
   عند الشك: `full`.
2. **حدّث شجرات نور الحقيقية** إن أمكن (مهارة `noor-tree`): المالك اشترط اختبار كل شجرة حقيقية قبل كل إصدار.
3. **ارفع الرقم:** `node tools/bump.mjs` (أو رقمًا محددًا). المتجر يرفض رقمًا ليس أعلى مما رُفع إليه.
4. **شغّل الاختبارات** (ساعات في full؛ شغّلها في الخلفية ولا تشغّل اختبارًا آخر بالمتصفح معها):
   ```bash
   node tools/suite.mjs --tier full --version <X>
   ```
   تبني خطوة gate الملفين `/mnt/project-files/afaq-platform/chrome-store/hader-store-<X>.zip` و`release/hader-extension-<X>.zip` وتحذفهما إن فشلت.
5. **إن فشلت خطوة:** افتح سجلها (المسار مطبوع)، أصلح السبب في الكود (لا تُضعف اختبارًا ولا تتخطّه)، ثم أعد الخطوة وحدها `--steps <name>` وبعدها الكل.
6. **سلّم:** ادمج طلب الدمج الخاص بك فقط (خيوط أخرى تفتح طلبات أيضًا)، وأرفق zip المتجر في ردك مع سطر الخلاصة كما طبعته الأداة، مثل:
   `SUITE PASSED — align 35/35, rich 0, matrix 240/240 (11051), oneper 240/240, real 35/35 (1447), scenarios 19/19, gate 14/14`
7. بعد رفع المالك للمتجر: مهارة `versions` تتحقق أن المتجر يعرض النسخة الجديدة.
